Problem
Cloud backup tools either upload terabytes of re-downloadable media and raw outtakes or rely on destructive sync rules that can wipe cloud copies after a local mistake.
What I built
A Windows desktop utility that groups folders into Standard, Source-Backed, and Immich buckets, encrypts uploads through rclone, and exports a standalone disaster recovery kit.

My personal Windows PC

Predictable, non-destructive backups with full data ownership. Encrypted files live in my own cloud storage in an open format, so recovery never depends on a backup vendor still being in business three years from now.

The problem

Backing up a Windows workstation with mixed files creates a costly tradeoff. Documents and project folders need full encrypted copies, while massive asset packs and raw camera libraries quickly overrun cloud storage and daily transfer caps. Most backup tools treat folders as flat file trees, forcing you to either upload terabytes of replaceable data or exclude whole directories and risk losing irreplaceable originals mixed inside. Rather than sorting folders by hand for a backup tool, I wanted the library apps I already use to drive backup decisions through ratings, tags, and lightweight source receipts, without relying on fragile scripts.

How it works

  1. Person

    The user connects an encrypted cloud remote once and validates the connection inside Settings.

    rcloneBackblaze B2Google Cloud
  2. Code

    Folders are organized into three bucket types: Standard for full encrypted copies, Source-Backed for re-downloadable asset packs, and Immich for rated and tagged photo or video libraries.

    Windows (WPF)
  3. Code

    Before uploading, Backup Bucket scans local files, computes SHA-256 fingerprints, and plans deduplicated cloud objects without touching local data.

    .NET 8
  4. Code

    For Source-Backed buckets, the app backs up small JSON receipt files recording each pack's source URL, version, and checksum instead of the multi-gigabyte archive, and flags uncovered folders so irreplaceable originals can be marked Unique.

  5. Code

    For Immich buckets, the app queries the library API by star rating and include or exclude tags, then adopts matching companion sidecar files.

    Immich
  6. Code

    Transfers run through non-destructive copy commands, paced by a rolling 24-hour upload cap and saved to a local history database.

    SQLite
  7. Code

    Every run writes a plain-English Markdown health report, a JSON recovery manifest, and a CSV recovery map when source-backed packs are present.

  8. Person

    When a restore is needed, the user picks files in the Backup Browser and restores them into a separate folder without overwriting existing files, or uses the exported recovery kit on a new PC.

Decisions and guardrails

  • Normal runs never delete or overwrite files. Every standard backup uses copy commands rather than destructive sync, and every restore writes to a separate folder with overwrite protection turned on. Deleting a bucket's cloud folder requires opening a dedicated removal dialog and typing the exact bucket name.
  • Deterministic code owns every file operation. There is no AI model in the backup or restore path. Hashing, upload planning, snapshot retention tiers, and quota enforcement run in local C# code and SQLite, and the exported recovery kit includes a plain-text AI recovery runbook so an assistant can guide a safe restore on a new PC without printing secrets or running delete commands.
  • Secrets stay locked to Windows and out of exports. Stored API keys use Windows current-user encryption, and the optional Backup Browser lock verifies passwords with 600,000 PBKDF2-SHA256 iterations. Exporting a recovery kit strips API keys and the browser password verifier before writing the archive.
  • Real transfers drove the pacing, checkpoints, and storage switch. Running large libraries hit daily provider caps and interrupted uploads, so I added a rolling 24-hour upload cap, automatic 24-hour rate-limit cooldowns, and resume checkpoints that continue without rescanning from scratch. Iterating on optimal rclone settings also led me to move the cloud backend from Google Cloud to Backblaze B2.
  • Recovery works without installing Backup Bucket. The disaster recovery kit bundles the active cloud remote configuration with plain-English instructions so files can be decrypted and restored on a fresh Windows PC using rclone alone.

What I'd change next

  • Add automated restore verification drills that periodically download and checksum a random sample of backed-up files to prove end-to-end recoverability.
  • Support direct cloud-side orphan pruning after a retention review, keeping human confirmation mandatory before removing unreferenced content objects.
  • Package a signed Windows installer with automatic update checks alongside the portable build.
